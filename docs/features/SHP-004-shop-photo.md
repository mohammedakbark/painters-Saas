# Feature: Shop photo and portable media storage

- **Feature ID:** SHP-004
- **Status:** Complete (local verification; see §13)
- **Last updated:** 2026-11-04
- **Related modules:** API (`src/storage/`, `src/media/`, `src/shops/shop-photo*`), web portal (`/shops/[shopId]/profile`), Shop App (shop profile screen), local Supabase Storage (`infra/supabase/config.toml`)
- **Decisions:** D-012 (photo required before going live), D-028 (free tiers, replaceable providers), ADR 0007

## 1. Problem and goal

A shop needs a photo before it can go live (D-012), and platform admins review it (PLT-002). The owner uploads one photo of the shop front on the web portal; the Shop App and, later, the Customer App show it. Storage must be free now and replaceable later (D-028).

## 2. User roles and permissions

| Role | Can | Cannot |
|---|---|---|
| Shop master | Upload or replace the photo (web) and see it (web, Shop App) | Upload for another shop (404) |
| Future staff roles | See the photo | Change it (403 `shop_permission_denied`) |
| Non-members and platform admins | Nothing through the shop routes (404) | — |

The image itself is public (a public bucket) because customers will see it. Its URL contains random identifiers and is not listed anywhere.

## 3. Preconditions

- The shop is registered (SHP-001).
- Local development: `pnpm supabase:start` (Storage plus the `shop-media` bucket) and the `STORAGE_*` variables in `apps/api/.env`.

## 4. User flow

1. On **Profile**, the **Shop photo** section shows the current photo or "No photo yet".
2. The owner chooses a JPEG, PNG or WebP file (on phones the browser can take a photo). A local preview appears.
3. **Upload photo** sends it. The page shows "Photo saved" and the new photo; the checklist item **Shop photo** becomes **Done**.
4. The Shop App's **Shop profile** shows the photo.

Failure paths:
- **Over 5 MB:** refused in the browser, and by the API with 413.
- **Another file type, or HEIC:** refused in the browser by type; by the API from the actual bytes.
- **Not an image, or truncated:** "This file is not a readable image."
- **Shorter side under 300 px:** "too small".
- **Storage unavailable:** 503 "The photo couldn't be stored right now. Try again." Nothing changes.
- **Image that can't load in the Shop App:** "The photo couldn't be loaded."

## 5. Business rules

1. One photo per shop; a new upload replaces it. Both old objects are deleted after the new photo is saved (best effort; failures are logged without keys).
2. Accepted: JPEG, PNG and WebP, up to 5 MB, with a shorter side of at least 300 px. HEIC is not accepted, because the prebuilt image library cannot decode it; iPhones convert to JPEG when the page asks for these types.
3. Every upload is decoded and re-encoded:
   - the camera orientation is applied;
   - all metadata (EXIF, including a phone's GPS position) is removed;
   - two WebP sizes are stored: at most 1600 px and at most 480 px.
4. Object keys are generated by the API: `shops/<shopId>/photo/<uuid>-1600.webp` and `-480.webp`. A CHECK constraint ties the key to its shop. Keys are immutable, so images are cached for a year.
5. The database stores the key prefix and the time only; URLs are derived from configuration (ADR 0007).

## 6. UI requirements

**Web:**
- `ShopPhotoForm`: a 4:3 frame with the current photo, a preview or "No photo yet"; a labelled file input; a pending state; errors announced (`role="alert"`).
- Read-only for members who can't edit.
- Submission runs in a transition (like the profile form); without JavaScript the form still posts.

**Shop App:**
- A 4:3 photo card above the address, with a loading indicator, an error text and a "Shop photo" semantics label.
- "Not added yet" when there is no photo.

## 7. API contract

`PUT /v1/shops/:shopId/photo`:
- **Access:** `@ShopScoped()`, MASTER only.
- **Request:** `multipart/form-data` with a single `photo` file. Limits: 5 MB, 1 file, no other fields.
- **Response:** the updated `ShopProfile`, which now includes `photo: { url, thumbUrl, updatedAt } | null`.

| Status | `code` | When |
|---|---|---|
| 400 | `photo_required` | No file |
| 400 | `photo_unsupported_type`, `photo_heic`, `photo_unreadable`, `photo_too_small` | Rejected image |
| 413 | — | Over 5 MB (multipart limit; detail "The upload is too large.") or `photo_too_large` |
| 403 | `shop_permission_denied` | Not the owner |
| 404 | `shop_not_found` | Not a member |
| 503 | `storage_unavailable` | Storage failed; nothing changed |

`GET /v1/shops/:shopId/onboarding` gains the item `photo`.

## 8. Data model and migrations

Migration `20261104072652_shp_004_shop_photo` adds `shops.photo_key` and `shops.photo_updated_at`. A CHECK requires both or neither, and requires the key to match `^shops/<id>/photo/<uuid>$`.

## 9. Security and privacy

- **Credentials:** the storage credentials (`STORAGE_S3_*`) are server-only. They are not in the web bundle, the APK or the logs (checked).
- **Content:**
  - every image is re-encoded, so only real JPEG, PNG or WebP content becomes public;
  - decompression bombs are limited (40 megapixels);
  - EXIF and GPS data are removed (checked on the stored objects);
  - storage SDK errors are wrapped so endpoints and keys don't reach clients.
- **Tenant boundary:** another shop's owner gets 404 and nothing is stored (e2e). The key prefix contains the shop id, enforced by a CHECK.
- **Audit:** `shop.photo_updated` records `replaced`, `width` and `height`; never the key or URL.
- **Public bucket:** for shop and product images only. Identity documents need a separate private bucket (`DATA_AND_SECURITY.md`).

## 10. Acceptance criteria

- [x] The owner can upload a photo on the web; it appears on the profile, the checklist shows **Shop photo: Done**, and the Shop App shows it.
- [x] Both stored sizes are WebP, at most 1600 px and 480 px, with no EXIF or GPS data, and are cached for a year.
- [x] Replacing the photo deletes the old objects.
- [x] Wrong type, unreadable, too small, over 5 MB and missing-file uploads are refused with a clear message, and nothing is stored.
- [x] When storage is down, the API answers 503 and the shop is unchanged.
- [x] Another shop's owner gets 404 and nothing is stored.
- [x] No storage credential is in the web bundle, the APK or the logs.

## 13. Implementation notes

**API:**
- `src/storage/`: `ObjectStorage`, `S3ObjectStorage` and `StorageModule` (global).
- `src/media/image-processor.ts`: sharp 0.35.5 (prebuilt binaries; `allowBuilds` still denies its install script).
- `src/shops/shop-photo.ts` (keys and URLs) and `shop-photo.service.ts`.
- `PUT /photo` in `shop-profile.controller.ts`, with multer limits.
- The problem filter gives 413 a client-safe detail.
- env `STORAGE_S3_ENDPOINT`, `STORAGE_S3_REGION`, `STORAGE_S3_ACCESS_KEY_ID`, `STORAGE_S3_SECRET_ACCESS_KEY`, `STORAGE_S3_FORCE_PATH_STYLE`, `STORAGE_BUCKET`, `STORAGE_PUBLIC_BASE_URL`; CI and e2e use placeholders.
- e2e use `FakeObjectStorage` (`test/support`).

**Local Supabase:**
- `[storage]` is enabled with `[storage.s3_protocol]`; image transformation is off; bucket `shop-media` is public, 5 MiB, `image/webp` only.
- The CLI creates config buckets only with `supabase seed buckets`, so `pnpm supabase:start` now runs it after `start`.

**Web:**
- `photo-form.tsx`, `photo-actions.ts` and `lib/shops/photo.ts`.
- `apiRequest` sends `FormData` as multipart.
- `uploadShopPhoto`.
- `experimental.serverActions.bodySizeLimit: '6mb'` in `next.config.ts`.
- Checklist label "Shop photo".

**Shop App:** `ShopPhoto` model and `_PhotoSection`. Widget tests now use a phone-sized screen: with the 800×600 default, scrolling to the location button made one test hang.

**Found during the live checks:** the first upload failed with 503 because the local bucket did not exist. The CLI doesn't create config buckets on `start`; fixed in `pnpm supabase:start`.

**Verified locally (2026-11-04):**
- **Chrome** (this computer):
  - the owner uploaded a test JPEG with GPS EXIF: "Photo saved", the photo shown, the checklist at 4 of 4;
  - a replacement upload: old objects return 400 from storage, the new ones 200;
  - audit `replaced: false` then `true`.
- **Storage over HTTP:** both sizes `image/webp`, `cache-control: public, max-age=31536000, immutable`, 1600×1200 and 480×360, no EXIF, no camera text.
- **Android emulator:** the photo is shown on the shop profile (through `adb reverse tcp:54321 tcp:54321`).
- **Builds and logs:** no storage or Supabase secret in the APK, the web bundle or the API log.
