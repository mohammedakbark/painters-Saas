# ADR 0006: API Conventions

- **Status:** Accepted (implemented in AUTH-001)
- **Date:** 2026-11-03
- **Decision owners:** Engineering

## Context

`TECHNICAL_ARCHITECTURE.md` §9 asks for a REST API with an OpenAPI contract, consistent errors, validation at the boundary, pagination and no leaked internal models. Open questions 43 (validation library) and 44 (versioning prefix and error shape) were to be decided with the first business endpoint, which AUTH-001 introduces (`GET /v1/me`).

## Decision

1. **Versioning:** every business route is under the URI prefix **`/v1`**.
   - `GET /health` and `GET /health/ready` stay unprefixed: hosting health checks call them.
   - The prefix is applied in `configureApp` (`apps/api/src/app.setup.ts`), which `main.ts`, the OpenAPI export and the e2e tests all use.
2. **Deny by default:** a global `AuthGuard` (APP_GUARD) requires a valid bearer token on every route. Public routes opt out with `@Public()`. Role checks are extra guards on top, for example `@PlatformAdminOnly()`.
3. **Validation:**
   - Request schemas are **Zod 4**, attached through Nest 12's built-in Standard Schema support (`@Body({ schema })`, `@Query({ schema })`, `@Param(name, { schema })`) and checked by the global `StandardSchemaValidationPipe`.
   - The parsed value is what the handler receives; unknown keys are stripped.
   - The same schemas produce the OpenAPI document. Zod's Standard JSON Schema output is converted by `@nestjs/swagger`, and responses use `@ApiOkResponse({ standardSchema })`.
   - This resolves question 43 in favour of Zod over class-validator: no decorators and no second validation library.
4. **Errors:** every error is **RFC 9457 problem details** with media type `application/problem+json`:

   ```json
   { "type": "about:blank", "title": "Bad Request", "status": 400,
     "detail": "The request is invalid.", "code": "validation_failed",
     "errors": [{ "path": "master.phone", "message": "Enter a valid mobile number." }] }
   ```

   - `code` is a stable, machine-readable extension that clients branch on.
   - `errors` lists field problems with dotted paths.
   - Expected errors are thrown as `ProblemException`, whose `detail` must be client-safe.
   - Framework 4xx errors get generic details.
   - Unexpected errors become a bare 500. The error name and stack are logged on the server; no internal message reaches the client.
   - 401 responses carry `WWW-Authenticate: Bearer` (plus `error="invalid_token"` when a token was rejected).
5. **Identifiers:** primary keys are **UUIDv7** (time-ordered, generated by Prisma). Timestamps are `timestamptz(3)`. Database names are snake_case (`@@map`/`@map`); Prisma and JSON names are camelCase.
6. **Pagination (for list endpoints, starting with PLT-001):** cursor-based. Requests take `limit` (default 20, maximum 50) and `cursor`; responses are `{ items, nextCursor }` and `nextCursor` is null on the last page.
7. **No CORS:** the web portal calls the API only from its server, and the mobile apps are not browsers. CORS is added only if a browser client ever calls the API directly.
8. **Schema changes** are Prisma migrations. Hand-written SQL in a migration (CHECK constraints, partial indexes, triggers, RLS) is commented in both the migration and `schema.prisma`. CI fails when `schema.prisma` and the migrations diverge (`db:check-drift`).

## Consequences

- Clients (web now, Flutter in SHP-001) parse one error format and map `errors[].path` to form fields.
- Response DTOs are explicit Zod schemas, so Prisma models are never returned as-is.
- Typed client generation from `packages/api_contracts/openapi.json` stays deferred. Until then, clients keep small hand-written response schemas next to their API calls, and those must be updated with the contract.
